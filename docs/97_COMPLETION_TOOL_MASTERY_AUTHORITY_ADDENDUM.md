## Decision question

Do the existing 14 Tool Mastery Upgrades all earn completion-bearing status as genuine capability/handling changes, and how do we prevent this category from becoming percentage stat filler or hidden mandatory progression?

## Fresh research conclusion

**Keep all 14 existing Tool Mastery Upgrades.**

The current catalog survives individual scrutiny because every upgrade changes an authored possibility, handling mode, state relationship, or interaction grammar. None of the fourteen is merely `+10% damage`, `+5% speed`, larger generic capacity, or a passive number bump.

The category therefore remains exactly what `docs/13` intended:

> **Mastery Upgrades change what the tool can meaningfully do or how the player can intentionally operate it.**

A second conclusion is also required: the old Cantor Key Fault-threshold sources cannot be consumed literally after Completion Decision #2 reduced Resonance Faults from 48 to 36. `K01 Field Memory` and `K02 Fine Fork` remain valid upgrades, but their numeric Fault milestones must be reconciled against the new 36-Fault track rather than preserving obsolete `6` / `30` assumptions by inertia.

## Locked philosophy

> **A mastery upgrade earns its slot by changing a verb, not by fattening a number.**

## Why the 14 survive

Each current upgrade passes at least one strong qualitative test:
- enables a new controlled state the base tool cannot hold;
- adds a new authored manipulation mode;
- changes handling enough to create different route/combat/puzzle decisions;
- supports new synthesis between existing systems;
- improves diagnostic capability in a way that creates new readable interactions rather than hidden numerical efficiency.

Examples:
- Brake Reel creates an intermediate catch/reclaim operation;
- Twin Chamber can hold two distinct authored pressure states;
- Bimetal Palm maintains two thermal zones rather than averaging one;
- Crossstay creates one deliberate lateral correction in valid airflow;
- Duplex Head can sustain two linked authored local states on paired nodes;
- Switchshoe changes supported-route junction behavior rather than simply increasing Skiff speed.

Those are real verb/handling changes.

## Optional-power ceiling

All 14 Tool Mastery Upgrades are treated as **optional completion content** unless a future explicit progression revision promotes one.

Critical-path design rules:
- ordinary mandatory story traversal cannot require any of the fourteen;
- mandatory bosses/encounters cannot be balanced assuming the player owns all or most upgrades;
- upgrades may open alternate routes, safer handling, richer optional puzzle solutions, special combat interactions, or faster/cleaner completion play;
- optional mastery content may require specific upgrades where the content clearly advertises that advanced requirement;
- the final critical path may acknowledge owned upgrades with alternate opportunities, but must preserve a valid baseline route.

The player who reaches credits with few/no optional upgrades still gets a complete game, not a deliberately crippled toolset.

## What qualifies as a Tool Mastery Upgrade

A completion-bearing Tool Mastery Upgrade must satisfy all of:
1. belongs to one established player tool/system;
2. adds a distinct capability, mode, control option, or authored handling relationship;
3. creates meaningful downstream uses beyond the acquisition scene;
4. has stable semantic identity;
5. is permanently learned/installed/available once earned;
6. does not merely reproduce a Cantor Pattern, story verb, accessibility setting, or generic stat increase.

### Forbidden mastery filler
The following do **not** qualify as Tool Mastery Upgrades:
- flat damage percentage;
- flat cooldown reduction with no new decision;
- generic range increase whose only effect is larger numbers;
- larger ammo/capacity pool with no authored state relationship;
- arbitrary movement-speed bonus;
- generic "rare tier" version of an existing upgrade;
- one-use key disguised as an upgrade.

Numerical tuning may support a qualitative capability, but numbers alone cannot justify the completion ID.

## Upgrade versus Cantor Pattern

Decision #8 remains authoritative:
- **Cantor Pattern:** operational knowledge/procedure applied through Cantor;
- **Tool Mastery Upgrade:** physical or operational capability/handling change to a tool/system.

Examples:
- Breath Ledger = knowledge/procedure for reading pressure history;
- Metered Valve = physical Glasslung handling mode for low-volume discharge.

If a future upgrade and Pattern appear to grant the same player-facing capability, production must resolve the duplication before either is implemented as separate completion authority.

## Upgrade versus major story verb

Major story verbs are not "mastery upgrades" simply because they permanently expand capability.

Anchor Line, Glasslung Reed, Temper Gauntlet, Vane Cloak, Mirror Nail, seam-state capabilities, and other critical-path systems remain progression authority outside this 14-item optional category.

Completion does not manufacture a second optional copy of story progression.

## Acquisition semantics

A Tool Mastery Upgrade counts when its authoritative progression transaction settles into `Acquired/Installed/Learned` according to that tool's fiction.

Possible authored sources include:
- Skill Trial mastery threshold;
- Repair Contract resolution;
- specialist Refuge service;
- Resonance Fault milestone;
- Micro-vault component + explicit fitting/assembly step;
- cross-system authored side activity.

Completion does **not** require:
- using the upgrade N times;
- clearing every downstream use;
- opening its catalog page;
- maxing a score after acquisition;
- buying a second generic tier.

## Fault-threshold reconciliation — K01 / K02

The old catalog says:
- K01 Field Memory — source: **6 Resonance Fault threshold**;
- K02 Fine Fork — source: **30 Resonance Fault threshold**.

Completion Decision #2 reduced the Fault track to **36**, and intentionally locked milestone **classes** while leaving exact numeric thresholds for later balancing/reconciliation.

Therefore:
- K01 remains the **early Fault-family milestone** Cantor upgrade;
- K02 remains the **late Fault-family milestone** Cantor upgrade;
- the literal `6` and `30` figures in `docs/13` are now **PROVISIONAL / SUPERSEDED AS FIXED AUTHORITY**;
- exact final thresholds must be selected during Issue #8 cumulative reconciliation against the 36-Fault cadence, without changing the qualitative function of K01/K02;
- no implementation may hardcode `30/48` logic from old planning documents.

A reasonable tuning study may still land near the old early fraction and a high-but-not-near-total late fraction, but this decision does not silently choose new numbers.

## Source diversity

The existing source policy remains good and is locked as a production constraint:
- Skill Trials can award handling mastery;
- Repair Contracts can award capability earned through understanding a person/system;
- Fault milestones can award diagnostic mastery;
- Refuges can provide specialist fitting/service;
- Micro-vaults may provide components but should generally not hand out a finished capability with no context.

No universal currency shop sells the fourteen completion-bearing mastery upgrades as a checklist.

## Downstream-use requirement

Every shipping Tool Mastery Upgrade must have at least **three meaningful authored downstream uses**, ideally spanning more than one domain (traversal / puzzle / combat-pressure / diagnosis / world utility) where the upgrade supports that breadth.

One-off gimmick upgrades fail review even if the one scene is fun.

The current catalog/revisit matrix already satisfies this direction conceptually; production implementation must keep it true as content is cut or rearranged.

## Accessibility / controls

A new handling mode must not quietly become inaccessible.

Required production checks:
- any new input is remappable or integrated into an existing accessible context action;
- state/mode activation is visually/textually readable and not color-only;
- timing/precision demands introduced by the upgrade respect project accessibility settings;
- rejection/eligibility is explainable rather than silent;
- hold/toggle alternatives are supported where project input policy requires;
- an optional upgrade cannot be the only accessible way through mandatory content.

Accessibility settings do not count as mastery upgrades and do not change completion entitlement.

## Missability / recovery

All 14 completion-bearing upgrades must remain obtainable during the natural completion sweep.

If an original NPC/source becomes inaccessible:
- a changed-world specialist/refuge/archive route may preserve the same upgrade opportunity;
- semantic upgrade ID stays unchanged;
- recovery cannot duplicate the permanent capability;
- an upgrade tied to a Trial/Contract must follow that activity's locked recovery/missability rules.

No story phase silently bricks 14/14.

## Persistence ownership

Inventory & Tool Progression / Player Progression owns upgrade acquisition/installation state.

Completion Ledger derives `upgrade.<tool>.<slug>` satisfaction from the settled progression fact.

Rules:
- stable semantic IDs, not Blueprint/object paths;
- one permanent acquisition fact per upgrade;
- fitted visual component is representation, not identity;
- save/load/retry cannot duplicate the capability/reward;
- migration explicitly handles rename/split/merge/retirement;
- downstream authored state remains owned by the relevant gameplay/world system.

## Tool Mastery / Completion System IDE

The shared development workbench must expose:
- upgrade semantic ID;
- owning tool/system;
- source activity / gate;
- acquired/installed state;
- qualitative capability tags;
- authored downstream-use references;
- optional/mandatory classification;
- progression owner fact;
- Completion Ledger reconciliation;
- input/control surface introduced;
- accessibility coverage;
- canonical/effective numerical tuning where the qualitative capability uses tunable values;
- duplicate-overlap validator against Cantor Patterns / story verbs / other upgrades;
- obsolete threshold-reference validation for K01/K02.

Required fixtures:
1. base tool without upgrade;
2. acquire/install one mastery upgrade;
3. save/load persistence;
4. duplicate acquisition rejected/idempotent;
5. optional upgrade absent on critical-path route;
6. upgrade used in traversal, puzzle, and/or combat-pressure downstream scenarios as appropriate;
7. Pattern-vs-Upgrade duplication validator;
8. inaccessible/timing-heavy control test with accessibility settings;
9. K01/K02 milestone source driven by reconciled completion data rather than hardcoded old totals;
10. 13/14 late completion audit.

## Red-team / rejection conditions

Reject a Tool Mastery Upgrade if:
- its only meaningful description is a percentage/stat increase;
- it duplicates a Cantor Pattern or major story verb;
- it has only one downstream use;
- mandatory story content assumes it without explicit progression revision;
- it is sold through repetitive currency/material grind as the only acquisition path;
- it becomes permanently missable through ordinary story progression;
- it introduces inaccessible mandatory controls with no accommodation;
- its acquisition or save/load can duplicate permanent capability;
- it exists only to preserve the number fourteen.
