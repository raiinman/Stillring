## Cumulative player-facing contract

### Cantor Key
The Key is a deliberate diagnostic/procedural instrument.

Base interaction:
1. player deliberately invokes Listen toward current view intent;
2. system evaluates a bounded visible local diagnostic relationship;
3. result is clear/ambiguous/not-actionable/none/blocked;
4. a clear candidate may become temporary diagnostic focus;
5. known applicable procedures may be selected;
6. the player may re-measure after world state changes.

The Key is not broad detective vision, treasure radar, through-wall objective scanning, or a memorized-song keycard system.

### Anchor Line
The Line creates one authored load path and applies/holds/releases tension along it.

The endpoint's semantic constraint decides the consequence:
- movable load moves;
- fixed approved traversal anchor may move Neris through the authored traversal state;
- constrained mechanism moves only along its declared degree of freedom;
- detachable/releasable component follows its explicit release contract;
- one static brace may hold an authored relationship.

Base Anchor does not provide universal grappling, swinging, telekinesis, arbitrary object attachment, generic crowd control, direct damage, or hidden solution behavior.

### Synthesis
Cantor and Anchor combine by reading/changing the same explicit world state. There is no combined super-mode or combo button.

## Gate 3 Tool / Puzzle System IDE

The Tool/Puzzle IDE is a shared development workbench registered in the dev-only System IDE shell. It reads/mutates authoritative gameplay services rather than implementing a parallel rules engine.

### B. Author / Tune
Only reviewed prototype parameters are live-tunable, with canonical/session-override/staged/promoted provenance:
- candidate forgiveness/stickiness;
- acquisition/working range within prototype bounds;
- load/tension presentation bands and movement limits;
- traversal arrival/path tuning that does not change eligibility semantics;
- mechanism constraint/return/damping values;
- diagnostic/tuning feedback thresholds;
- accessibility timing/cue parameters.

The workbench may not live-author:
- new semantic response families;
- extra base braces;
- through-wall base Cantor authority;
- arbitrary objective-linked compatibility;
- direct Anchor damage/stun;
- hidden combo modes;
- changes to locked combat/camera/locomotion semantics.

Those require a new design decision.

## Deterministic fixture reset

Reset is transactional from the fixture's perspective.

A reset must:
1. reject/stop new fixture-scoped requests;
2. clear handheld Anchor ownership;
3. clear fixture-owned static brace state;
4. clear Cantor focus/transient procedure state;
5. restore participant actors/components to registered baseline identity/state/transform;
6. restore mechanism topology/state and fixture-local timers;
7. clear fixture-spawned transient hazards/projectiles/objects;
8. restore the declared player baseline when fixture-owned;
9. re-register participants and verify no duplicate/stale IDs;
10. resume input only after invariant validation succeeds.

Reset must not mutate unrelated story/quest/world persistence.

Tests must assume the previous run may have ended badly. This aligns with Epic's Automation Framework guidance to avoid assuming starting state and to clean up test-created state. Engine automation is useful execution infrastructure, not Stillring policy authority.

## Validate

Machine-verifiable Gate 3 invariants include:
- base Cantor does not acquire discrete targets through opaque blockers;
- objective/quest metadata cannot make a candidate compatible;
- diagnostic focus never overwrites combat target;
- base Anchor never has more than one static brace;
- force is zero through hard load-path obstruction;
- cable presentation does not own semantic load state;
- arbitrary fixed load point is not traversal-enabled;
- traversal does not chain midair without explicit authority;
- Anchor has no base health-damage or generic-stun result;
- latch alone does not produce reaction/stagger;
- puzzle completion corresponds to explicit mechanism invariants;
- identical semantic targets do not diverge because one is “the solution”;
- synthesis never creates a hidden third interaction mode;
- required tool actions are remappable;
- critical state does not rely on color/audio/haptics alone;
- reset leaves no stale endpoint/focus/brace/fixture ownership;
- development IDE/tooling is excluded or hard-disabled in Shipping;
- no retail runtime AI/model/API dependency exists in Tool/Puzzle runtime authority.

## Capture / reproduce

A Gate 3 capture record should contain:
- build/source/map/fixture IDs;
- deterministic seed if any;
- input device/mapping/accessibility settings;
- player state/camera/combat target context;
- timestamped Cantor requests/results/focus/procedure state;
- timestamped Anchor candidate/latch/tension/brace/traversal/combat request state;
- endpoint and mechanism semantic IDs;
- accepted/rejected request reasons;
- shared world-fact transitions and owning system;
- relevant raw physics/trace values as evidence, clearly labeled non-authoritative;
- reset operations/results;
- invariant pass/fail events;
- human notes/reference screenshots/video IDs where added.

Epic's Automation Framework can provide unit/feature/smoke/functional execution, export JSON/HTML/log results, and support fixtures; Gameplay Debugger can provide runtime overlays. These should augment the in-game workbench, not replace its semantic state/capture contract.

## Human-play authority

Automation does not close feel/readability.

Human Gate 3 prototype acceptance must eventually verify:
- Cantor is useful without scan-spam;
- Anchor targeting feels deliberate rather than fussy;
- reeling/tension feels responsive without becoming a weapon;
- traversal expands routes without trivializing locomotion/world boundaries;
- combat manipulation is readable under real encounter pressure;
- puzzle solutions feel inferred from mechanisms rather than socket matching;
- Cantor + Anchor synthesis is discoverable without solution highlighting;
- accessibility modes reduce input/perception barriers without solving the reasoning.

These remain implementation/human-play obligations, not reasons to reopen design semantics automatically.
