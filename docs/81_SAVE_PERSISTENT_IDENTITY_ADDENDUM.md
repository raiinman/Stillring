# 81 — Persistent World-State / Save Decision #1 — Stable Persistent Identity

**Status:** FINAL OWNER-DELEGATED APPROVAL  
**Updated:** 2026-09-05  
**Issue:** #4 — Define persistent world-state and save schema  
**Decision:** #1 — persistent ID format, ownership, lifecycle, and forbidden keys

## Decision question

What identifier may a save file use to refer to an authored world fact/entity across editor renames, World Partition/Data Layer representation changes, unload/reload, refactors, and future save-schema migrations?

## Locked philosophy

> **Save identity belongs to the authored game meaning, not to the current Unreal object instance.**

A persistence key must survive changes to runtime allocation, Actor instance, node path, object path, package arrangement, streaming state, and presentation layer whenever the underlying authored gameplay identity has not intentionally changed.

## Research basis

Fresh research against Unreal Engine 5.8 confirms several important boundaries:

- `USaveGame` is a general container for game state; the game decides what semantic state to populate and restore.
- Unreal `FGuid` is a stable 128-bit GUID value type suitable for project-owned durable identifiers.
- `AActor::GetActorGuid()` / `GetActorInstanceGuid()` are editor-oriented and explicitly unavailable as general runtime save identity; they are not the Stillring persistence contract.
- World Partition conversion itself validates Actor GUID stability because unstable Actor GUIDs can change conversion output. That is useful editor/source-control infrastructure, but does not make World Partition Actor identity the canonical save key.
- One File Per Actor and World Partition package/Actor layout are editor/representation concerns. They may change without changing a player's semantic world history.
- UE custom serialization/versioning uses project-owned `FGuid` + monotonically increasing versions, reinforcing the separation between durable semantic identity and incidental object/package paths.

## 1. Canonical persistent identifier type

Stillring uses a project-owned semantic identifier:

`FStillringPersistentId`

Conceptually it contains:
- one non-zero `FGuid` as the canonical machine identity;
- optional human-readable editor metadata for diagnostics only (`DebugName`, owning domain, source asset/reference), never serialized as the lookup key;
- optional identity class/domain enum for validation and tooling, not for uniqueness by itself.

The GUID is the authority. Human-readable names may change freely without changing persistence identity.

## 2. ID creation rule

Persistent IDs are **authored once and then preserved**.

For author-placed persistent gameplay entities/facts:
- the authoritative GUID is generated by Stillring tooling/editor workflow when persistence identity is first assigned;
- it is stored in repository-backed authored data alongside that semantic entity/fact;
- renaming, moving, reparenting, changing Data Layer, converting level representation, or moving between packages does not regenerate it;
- duplication creates a new GUID unless an explicit paired-identity workflow says both expressions intentionally share one semantic identity.

`FGuid::NewDeterministicGuid` may be useful for build tooling when its seed/path is itself guaranteed stable, but object paths are specifically not stable enough to be Stillring's default persistent-world identity. Therefore deterministic path hashing is **not** the canonical authoring rule for gameplay persistence IDs.

## 3. Identity ownership classes

Every persistent ID has exactly one semantic owner class.

### Authored world entity
Examples: a shortcut mechanism, boss identity, unique chest/interactable, named persistent NPC recurrence entity, Hush/Waking paired object.

The ID belongs to the semantic authored entity, not its current Actor instance.

### World fact / progression fact
Examples: bridge repaired, catastrophe occurred, boss defeated, conversation milestone reached, shortcut opened.

The ID belongs to the authored fact definition. Runtime Actors observe/apply the fact; they do not own its existence.

### Unique collectible / acquisition
The ID belongs to the authored collectible/acquisition occurrence, not to a spawned pickup Actor.

### Runtime-created persistent record
If Stillring later permits genuinely runtime-created durable entities, their IDs are minted at the moment the authoritative persistent record is created and thereafter treated exactly like authored persistent identity. Gate 0–vertical-slice scope does not require arbitrary player-created world entities, so this path remains narrow.

## 4. Waking / Hush compatibility

Gate 4 authority remains unchanged.

A paired Waking/Hush expression that represents one semantic entity uses **one semantic persistent ID**. Layer-specific representation Actors/components may have local representation identities for runtime/editor use, but save data refers to the semantic pair identity plus explicit state/fact data.

Layer-exclusive entities receive their own semantic persistent IDs when they own durable state.

Changing the active Hush/Waking representation must never create a second save identity for the same authored thing.

## 5. Explicitly forbidden canonical persistence keys

The following may appear in diagnostics or migration tooling but may **never** be the canonical save identity:

- UObject memory address / pointer;
- runtime spawn index;
- `GetUniqueID()` or equivalent process-local identity;
- Actor runtime instance name;
- Actor label;
- Blueprint node path;
- UObject full object path;
- map/level path by itself;
- package path by itself;
- World Partition cell/grid coordinate;
- Runtime Data Layer name/index;
- OFPA external-Actor encoded filename;
- array position/order;
- quest-node ordinal;
- current Actor `GetActorGuid()` / `GetActorInstanceGuid()` as the Stillring semantic save contract;
- display/localization string;
- coordinates/transform as identity.

These are implementation/presentation details and may change while gameplay meaning remains the same.

## 6. Rename / move / refactor behavior

A semantically identical authored entity keeps its persistent ID through:
- Actor rename;
- editor label rename;
- map/package move;
- sublevel → World Partition conversion;
- Data Layer reassignment;
- Waking/Hush representation refactor;
- Blueprint → C++ authority migration;
- Actor decomposition into components or consolidation of representation Actors;
- art replacement;
- ordinary source-control file movement.

If gameplay meaning is intentionally replaced by a different semantic entity, assign a new ID and handle old-save translation through the migration contract rather than silently reusing the old ID.

## 7. Duplicate / copy-paste safety

Editor tooling must detect duplicate persistent GUIDs.

Default copy/duplicate semantics:
- duplicated persistent entity gets a new GUID;
- duplicated visual-only representation with no independent semantic persistence may retain no persistent ID;
- Hush/Waking paired authoring uses an explicit pairing operation to share one semantic ID rather than accidental copy/paste duplication.

A duplicated GUID in two unrelated semantic owners is a **hard validation error** before content merge/package.

## 8. Deleted content and tombstones

Deleting an authored entity does not authorize immediate reuse of its GUID.

Persistent GUIDs are never recycled. If old saves may contain the ID, migration may:
- translate it to a replacement semantic ID;
- consume/drop the obsolete record deliberately;
- convert it into a replacement world fact;
- reject the save only under the later incompatible-save policy.

This prevents a deleted chest's old state from accidentally applying to a new boss because someone reused an ID.

## 9. Runtime lookup contract

Runtime systems resolve persistence records through a semantic registry/service:

`FStillringPersistentId -> authoritative semantic owner / state adapter`

Actors register/unregister their semantic representation as streaming/layer state changes. Save state exists independently of whether the representation is currently loaded.

A save load must therefore be able to ingest world facts for an entity before its Actor is streamed/instantiated, then apply the state when that semantic representation becomes available.

## 10. Validation rules

The Save / World-State System IDE and machine validation must detect:
- invalid zero GUID;
- duplicate GUID ownership;
- persistent entity with missing GUID;
- same GUID claimed by incompatible semantic classes;
- paired Hush/Waking expressions accidentally using separate semantic IDs where authority says they are one entity;
- unrelated layer expressions accidentally sharing one ID;
- save reference to unknown ID;
- retired/tombstoned ID with no migration disposition;
- use of forbidden path/name/runtime keys in persistence declarations;
- GUID changed between two revisions without explicit migration note.

## 11. System IDE requirements

The shared development shell receives a Save / World-State workbench.

### Inspect
For any loaded representation or save record show:
- canonical persistent GUID;
- human-readable debug name;
- semantic owner class;
- loaded/unloaded registration state;
- Waking/Hush pair relationship;
- source authority asset/file if known;
- persisted records currently attached to the ID;
- migration/tombstone status.

### Exercise
Development-only actions may:
- locate/select loaded representation by persistent ID;
- simulate unload/reload and verify reattachment;
- show both paired Hush/Waking expressions for one semantic ID;
- run duplicate/missing/unknown-ID validators;
- export an ID inventory for diff/review.

The IDE may **not** casually regenerate production IDs. Any deliberate identity replacement must be an explicit authoring action with migration consequences visible.

### Capture
Bug evidence involving persistence must include stable persistent IDs so a reproduction remains meaningful after Actors are renamed or moved.

## 12. Deterministic fixtures

### S1-F01 — rename stability
Save state against a persistent interactable, rename Actor/label, reload; state resolves to the same semantic ID.

### S1-F02 — package move stability
Move the representation between packages/level organization without changing semantic ID; old save still resolves.

### S1-F03 — streaming lifecycle
Persist state while representation is unloaded; later stream/load Actor and apply state exactly once.

### S1-F04 — duplicate authoring
Duplicate a persistent entity; validator proves the duplicate receives a different GUID.

### S1-F05 — accidental collision
Force two unrelated owners to share a GUID; validation hard-fails with both sources identified.

### S1-F06 — Hush paired identity
Waking and Hush expressions share one semantic ID and restore one coherent fact history.

### S1-F07 — layer-exclusive identity
Hush-only persistent entity restores correctly without manufacturing a Waking counterpart.

### S1-F08 — deleted ID
Load a fixture containing a retired ID; migration/tombstone handling is deterministic and never binds the record to an unrelated new entity.

### S1-F09 — unknown ID
Load a fixture with a syntactically valid but unknown GUID; later malformed/compatibility policy decides recovery, while tooling reports the exact unknown record.

### S1-F10 — representation refactor
Replace the underlying Actor/class representation while preserving semantic meaning and GUID; old save resolves through the new adapter.

## 13. Accessibility / player-facing implications

Persistent identity is mostly invisible to players, but its correctness protects accessibility and progression:
- remapped controls/settings and accessible progression must not be invalidated by content renames;
- assist settings must not change semantic IDs or save eligibility;
- layer/presentation accessibility modes cannot create divergent world history;
- recovery messaging for save problems must use human-readable names while diagnostics retain stable GUIDs.

## 14. IP boundary

This is an original project persistence architecture built from generic durable-ID/versioned-save engineering principles and Unreal's public engine primitives. No Nintendo/Zelda proprietary save layout, identifiers, reverse-engineered flag tables, or exact serialization format is used.

## 15. Rejected alternatives

### Object path as save key
Rejected: brittle under rename/package/refactor and contradicts the requirement that semantic world history outlive representation changes.

### Actor label/name as save key
Rejected: human/editor naming is not identity.

### World Partition Actor GUID as canonical save key
Rejected: useful representation/editor identity, but engine representation must not own Stillring semantic persistence. Actor GUID APIs are also editor-oriented.

### Data Layer + local object name composite
Rejected: Gate 4 explicitly treats Data Layers as representation, not canonical world truth.

### Integer table index
Rejected as the canonical identity: ordering/repacking creates migration hazards. Compact indices may exist inside a compiled runtime cache only if mapped from stable persistent IDs.
